# סעיף 6 – בדיקת ביצועים

## היקף

הבדיקה מתמקדת בשתי פעולות מרכזיות:

1. `GET /api/tickets` – סינון לפי סטטוס ועדיפות, ספירת תוצאות והחזרת עמוד של 20 פניות.
2. `GET /api/tickets/{id}/history` – בדיקת קיום הפנייה והחזרת יומן השינויים שלה.

ב־`TicketService.GetTicketsAsync` הסינון, הספירה, המיון וה־`Skip/Take` נשארים ב־EF Core כ־`IQueryable` ומתורגמים לשאילתות SQL. רק תוצאות העמוד נטענות ב־`ToListAsync`; אין טעינה מלאה של הפניות לזיכרון לפני הסינון והדפדוף. גם היסטוריית השינויים מסוננת לפי `TicketId` במסד הנתונים.

## הרצת הבדיקה

1. יש להשתמש במסד PostgreSQL או בסכמה ייעודית וריקה לבדיקות, ולא בטבלאות האפליקציה עם נתונים אמיתיים. בהרצה המתועדת כאן נעשה שימוש בסכמה זמנית נפרדת באותו פרויקט Supabase; הטבלאות הציבוריות לא שונו.
2. להחיל את מיגרציות EF Core על מסד/סכמת הבדיקה.
3. להריץ את `section-6-performance.sql` דרך `psql` או עורך SQL שמחובר למסד הבדיקה. בסכמה ייעודית יש להגדיר את `search_path` של החיבור לאותה סכמה; במסד בדיקה נפרד אפשר להשאיר את ברירת המחדל `public`. הסקריפט בודק שהטבלאות ריקות, מכניס 100,000 פניות ו־100,000 רשומות audit, ומריץ `ANALYZE`. אם הטבלאות אינן ריקות, הסקריפט נעצר בלי למחוק את הנתונים הקיימים.
4. להפעיל את ה־API מול אותו מסד בדיקה ולשלוח את הבקשות:

   ```text
   GET /api/tickets?status=InProgress&priority=High&page=1&pageSize=20&sortBy=CreatedAt&sortDescending=true
   GET /api/tickets/45c48cce-2e2d-7fbd-ea1a-fc51c7c6ad26/history
   ```

5. לשמור את פלט `EXPLAIN (ANALYZE, BUFFERS)` עבור כל שאילתות ה־SQL שבסקריפט. ברשימה נבדקות גם שאילתת הספירה וגם שאילתת העמוד, כי ה־API מריץ אותן בנפרד. בבקשות HTTP מומלץ לבצע חימום ואז לפחות 30 מדידות ולדווח חציון ו־p95.

`EXPLAIN ANALYZE` מודד את זמן ה־SQL בפועל. יש לתעד מתוכו את סוג הגישה (למשל `Index Scan`,‏ `Bitmap Heap Scan` או `Seq Scan`), זמן הביצוע, שורות בפועל וה־buffers שנקראו או נמצאו במטמון. אין להסיק מראש שהאינדקס ייבחר; יש לדווח על התוכנית שהתקבלה בפועל.

## אינדקסים קיימים

האינדקסים מוגדרים ב־`AppDbContext` ונוצרים במיגרציה הראשונית:

| אינדקס | שימוש מיועד |
| --- | --- |
| מפתח ראשי `tickets.Id` | שליפת פנייה ועדכון לפי מזהה |
| `tickets.Status` | סינון לפי סטטוס |
| `tickets.Priority` | סינון לפי עדיפות |
| `tickets.AssignedTo` | סינון לפי מטפל |
| `tickets.CreatedAt` | מיון לפי תאריך יצירה |
| `tickets(Status, Priority, CreatedAt)` | סינון משולב ומיון ברשימת הפניות |
| מפתח ראשי `ticket_audit_logs.Id` | זיהוי רשומת audit |
| `ticket_audit_logs(TicketId, ChangedAt)` | שליפת היסטוריה לפי פנייה ומיון לפי זמן |

לא נוסף בשלב זה אינדקס מעבר לאלה שבמיגרציה: יש לאשר צורך באינדקס נוסף על בסיס תוכנית הביצוע ומדידות, כדי לא להוסיף עלויות כתיבה ואחסון ללא ראיה.

## צווארי בקבוק ושיפורים אפשריים

- חיפוש הטקסט ב־`Title` וב־`OrganizationName` משתמש ב־`ILIKE '%term%'`. אינדקסי B-tree הקיימים לא יעילים בדרך כלל לתבנית שמתחילה ב־`%`. אם המדידות מראות שזה צוואר בקבוק, אפשר לבדוק את הרחבת PostgreSQL `pg_trgm` ואינדקסי GIN; יש לאמת את השיפור עם `EXPLAIN ANALYZE` לפני הוספתם למיגרציה.
- `CountAsync` סופר את כל ההתאמות בכל בקשת רשימה, ו־`OFFSET` עמוק עלול לסרוק ולדלג על שורות רבות. אם זמני הספירה או הדפדוף בעמודים גבוהים אינם עומדים ביעד, אפשר לשקול ספירה מקוטנת/מטמון או keyset pagination, תוך בחינת ההשפעה על חוזה ה־API.
- סטטיסטיקות כלליות שסורקות את הטבלה כולה עשויות להפוך ליקרות ככל שהטבלה גדלה. יש למדוד גם אותן אם הן חלק מהתרחיש המרכזי של המערכת.

## תוצאות מדידה

המדידה בוצעה ב־2026-09-27 על 100,000 פניות ו־100,000 רשומות audit בסכמה זמנית נפרדת בפרויקט Supabase. `EXPLAIN (ANALYZE, BUFFERS)` הורץ במסד; ה־HTTP נמדד מול מופע API מקומי שהתחבר לאותה סכמה. בוצעו 3 בקשות חימום ואז 30 דגימות לכל endpoint. החציון הוא ממוצע שתי הדגימות האמצעיות; p95 חושב לפי nearest-rank. לאחר המדידה מופע ה־API נעצר והסכמה הזמנית הוסרה. הטבלאות הציבוריות והנתונים הקיימים לא שונו.

| פעולה | שורות בבסיס הנתונים | זמן SQL | חציון HTTP | p95 HTTP | תוכנית / buffers |
| --- | ---: | ---: | ---: | ---: | --- |
| GET רשימה – count | 100,000 (8,333 התאמות) | 2.954 ms | לא נמדד בנפרד | לא נמדד בנפרד | Aggregate → Index Only Scan; 77 shared hits, 0 reads |
| GET רשימה – page | 100,000 (20 מוחזרות) | 0.102 ms | 468.937 ms לכל endpoint | 475.723 ms | Limit → Incremental Sort → Index Scan; 18 shared hits בשורש, 0 reads |
| GET היסטוריה – בדיקת קיום | 100,000 | 0.048 ms | נמדד יחד עם שליפת ההיסטוריה | נמדד יחד עם שליפת ההיסטוריה | Limit → Index Only Scan; שורה אחת, 4 shared hits, 0 reads |
| GET היסטוריה – שליפת audit | 100,000 פניות + 100,000 audit | 0.036 ms | 466.403 ms לכל endpoint | 471.733 ms | Index Scan; שורה אחת, 5 shared hits, 0 reads |

זמני ה־HTTP כוללים את זמן הרשת בין סביבת ההרצה המקומית ל־Supabase ואת שתי שאילתות ה־DB הנפרדות של endpoint הרשימה. לכן הם אינם מייצגים זמן SQL בלבד או בהכרח את זמני התגובה של ה־hosting. בתוכנית הרשימה נעשה שימוש ב־Index Scan וב־Incremental Sort; מדידת count השתמשה ב־Index Only Scan. בחיפוש `ILIKE '%term%'` עדיין צפוי צוואר בקבוק, מאחר שהאינדקסים הקיימים אינם מיועדים לחיפוש substring.
