# סעיף 7 – Cache

## מה נשמר ולמה

`GET /api/tickets/statistics` מחזיר ספירות לפי סטטוס ועדיפות, ונדרש שוב ושוב על ידי תצוגת העבודה. החישוב מבצע שתי שאילתות aggregation במסד; שמירת התוצאה מפחיתה קריאות DB חוזרות עבור מידע מסכם, שאינו משתנה בכל בקשה. פרטי כרטיס בודד לא נשמרים, משום שהם משתנים תדיר יותר.

## תפוגה וביטול

ה־API משתמש ב־`IMemoryCache` עם המפתח `ticket-statistics:v1` ותפוגה מוחלטת של דקה. לאחר יצירת פנייה או עדכון סטטוס מוצלח, השירות מסיר את הערך מהמטמון. עדכון שנכשל אינו מבטל את הערך; קריאת הסטטיסטיקות הבאה לאחר שינוי מוצלח מחשבת את הסיכומים מחדש. עדכוני bulk עוברים דרך אותו מסלול עדכון סטטוס ולכן גורמים לאותו invalidation.

התפוגה מגבילה את משך הזמן שבו מידע עלול להישאר מיושן גם במקרה של כתיבה ממקור אחר שאינו מפעיל את מנגנון הביטול של ה־API.

## מספר מופעי שרת

`IMemoryCache` הוא מקומי לתהליך. בפריסה עם מופע שרת יחיד הוא מספק את ההתנהגות הנדרשת; במספר מופעים, invalidation במופע אחד לא מסיר את הערך מהמטמון של האחרים. בפריסה כזאת יש להחליף אותו ב־`IDistributedCache` עם Redis משותף לכל המופעים, לשמור תחת אותו מפתח ו־TTL, ולמחוק את המפתח המשותף לאחר כתיבה מוצלחת. אם מוסיפים גם מטמון L1 מקומי בכל מופע, יש להפיץ אירועי invalidation בין המופעים, למשל באמצעות Redis Pub/Sub. אין בפרויקט כרגע תשתית Redis מוגדרת, ולכן היא נדרשת כחלק מהרחבה לפריסה מרובת מופעים.
