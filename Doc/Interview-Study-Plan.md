# תוכנית לימודים לראיון עבודה

התוכנית מבוססת על תחומי המבדק והמשקלים במסמך `מבחן_FULL_STACK_רמה_ג_מעודכן.pdf`. היא משלבת חזרה על עקרונות עם תרגול מתוך Ticket Management. מומלץ להקדיש 60–90 דקות לכל מפגש ולענות בקול על שאלות הסיכום כאילו מדובר בראיון.

## דרישות שכדאי לבדוק מול המימוש

ה־PDF דורש יותר מכפי שכדאי להסיק מכך שהמערכת עובדת. לפני הראיון, הבחן בין דרישה, מה שממומש כרגע ומה נשאר לשיפור:

| דרישה במבדק | מצב בפרויקט / נושא לחזרה |
| --- | --- |
| לפחות 100,000 רשומות ויצירה חוזרת של נתוני בדיקה | סקריפט סעיף 6 יוצר 100,000 שורות, אך נעצר אם הטבלאות אינן ריקות. כדי לחזור על הבדיקה, משתמשים במסד/סכמה זמניים חדשים או מוסיפים reset ייעודי ובטוח לסביבת בדיקה בלבד. |
| סינון משולב לפי Status, Priority, AssignedTo, OrganizationName וטווח תאריכים | כרגע ה־API מסנן במפורש לפי Status, Priority ו־AssignedTo ומחפש substring ב־Title וב־OrganizationName. סינון נפרד לפי OrganizationName וטווח תאריכים הם פערים שכדאי להכיר ולממש אם נדרש כיסוי מלא. |
| לפחות שתי Aggregations רלוונטיות | ה־statistics endpoint מסכם לפי Status ולפי Priority. תרגל איך כל קבוצה מתורגמת ל־`GROUP BY` ומה המסך עושה עם התוצאה. |
| Audit הכולל מזהה בקשה ומי ביצע | קיימים `TicketId`,‏ `OldStatus`,‏ `NewStatus` ו־`ChangedAt`; `ChangedBy` nullable ואינו מאוכלס כרגע, ואין עמודת `RequestId` נפרדת. הסבר ש־`TicketId` מזהה את הפנייה, אך הוא אינו מזהה בקשה/פעולה ייחודית. |
| בדיקות מול מסד | ארבע הבדיקות משתמשות ב־SQLite ומכסות stale-version conflict דרך ה־API, אך לא התנהגות PostgreSQL ייחודית ולא מרוץ מקביל מתוזמן של שני HTTP requests. |

המטרה אינה להציג פערים כמימוש שהושלם. הכן לכל אחד תשובה: מה קיים, מה חסר, מה הסיכון ומה השינוי המצומצם שהיית עושה.

## תוכנית ל־10 מפגשים

### מפגש 1 – הצגת המערכת וה־Backend

חזור על C# מודרני, `async`/`await`, `CancellationToken`, Dependency Injection, וההפרדה בין Controller, Service ו־DbContext.

תרגול בפרויקט: עקוב אחרי בקשת `GET /api/tickets` מה־Controller דרך `TicketService` עד EF Core, והסבר מה כל שכבה אחראית לעשות.

שאלת ראיון: למה לא לשים שאילתות DB ולוגיקה עסקית בתוך ה־Controller?

### מפגש 2 – REST API ו־Validation

חזור על HTTP verbs, status codes, DTOs, model binding ו־validation. הבחֵן בין 400 לקלט לא תקין, 404 למשאב חסר, 409 להתנגשות או מעבר אסור, ו־201 ליצירה. תרגל גם חוזה query שמכיל status, priority, assignedTo, organizationName, טווח תאריכים, search, sort ו־pagination.

תרגול: הצג את חוזה `POST /api/tickets` ואת `PATCH /api/tickets/{id}/status`, כולל תשובה מוצלחת וכשל.

שאלת ראיון: מתי מחזירים 400 ומתי 409?

### מפגש 3 – EF Core ו־PostgreSQL

חזור על migrations, מפתחות ראשיים וזרים, nullability, טרנזקציות, `IQueryable` מול `IEnumerable`, `AsNoTracking`, ותרגום LINQ ל־SQL. השווה PostgreSQL ל־SQL Server ול־MongoDB לפי קשרים, aggregations, אינדקסים, עסקאות ודרישות התפעול.

תרגול: צייר את הקשר בין `tickets` ל־`ticket_audit_logs`, והסבר למה pagination וסינון נעשים במסד ולא אחרי טעינת הנתונים לזיכרון. תכנן יצירה חוזרת של 100,000 רשומות בסביבת בדיקה, בלי לאפשר איפוס נתונים במסד production.

שאלת ראיון: מה ההבדל בין `Skip/Take` בצד המסד לבין הבאת כל השורות ואז סינון ב־C#?

### מפגש 4 – אינדקסים, חיפוש וביצועים

חזור על B-tree, אינדקסים מורכבים, selectivity, עלות כתיבה, `EXPLAIN (ANALYZE, BUFFERS)` ו־offset pagination. זכור ש־`ILIKE '%term%'` אינו נהנה בדרך כלל מאינדקס B-tree רגיל; `pg_trgm`/GIN יכול להיות חלופה אחרי מדידה. חזור על שתי ה־aggregations לפי סטטוס ועדיפות ועל השפעתן במסד עם 100,000 רשומות.

תרגול: פתח את `Doc/Section-6-Performance.md`, הסבר את תוכניות הביצוע ואת ההבדל בין זמן SQL לזמן HTTP הכולל רשת.

שאלת ראיון: איך תחליט אם להוסיף אינדקס, ומה המחיר שלו?

### מפגש 5 – Concurrency ו־Audit

חזור על lost update, optimistic concurrency, concurrency token, טרנזקציות ו־audit trail. דרישת ה־audit כוללת מזהה פנייה/בקשה, סטטוס קודם וחדש, זמן שינוי וזהות מבצע.

תרגול: הסבר תרחיש שבו שני משתמשים קוראים `Version=1`; הראשון מעדכן, והשני מקבל 409 כי הגרסה שלו מיושנת. עקוב גם אחרי השמירה של `TicketAuditLog` באותה פעולת `SaveChanges`, והסבר כיצד היית מעביר `ChangedBy` ו־request/correlation ID לשירות.

שאלת ראיון: למה לבחור ב־optimistic concurrency ולא לנעול את הרשומה בזמן העריכה?

### מפגש 6 – Bulk וגבולות טרנזקציה

חזור על batch processing, מגבלות גודל, כשל חלקי לעומת כשל אטומי, ועלויות של עדכון פריט־אחר־פריט.

תרגול: הסבר את `POST /api/tickets/bulk-status`: למה יש מגבלה של 100 פריטים, מה קורה כשפריט אחד נכשל, ומה מובטח ומה לא מובטח לכל הבקשה.

שאלת ראיון: מתי bulk צריך להיות all-or-nothing ומתי תוצאה פר־פריט מתאימה יותר?

### מפגש 7 – Angular ו־RxJS

חזור על standalone components, שירותי API, Signals ו־computed values, Reactive Forms, Observable, `debounceTime`, `distinctUntilChanged`, `switchMap` וביטול בקשות קודמות.

תרגול: הצג איך חיפוש המסך ממתין ל־debounce, איך מתמודדים עם חיפוש מהיר, ואיך Signals מחזיקים מצב loading/data/error.

שאלת ראיון: מתי תבחר Signal למצב UI ומתי Observable לזרם אסינכרוני?

### מפגש 8 – Cache

חזור על cache-aside, TTL מוחלט, invalidation אחרי כתיבה, stale data ו־cache stampede. הבחן בין `IMemoryCache` לתהליך יחיד לבין `IDistributedCache` משותף.

תרגול: הסבר למה סיכומי סטטיסטיקה נשמרים לדקה, למה יצירה/עדכון סטטוס מוחקים אותם, ומה צריך לשנות בפריסה מרובת מופעים.

שאלת ראיון: מה קורה אם עדכון הגיע למופע שרת אחר שלא מחזיק את אותו מטמון?

### מפגש 9 – בדיקות אוטומטיות

חזור על unit לעומת integration tests, test fixture, מסד זמני, isolation, arrange/act/assert, ובדיקת status code יחד עם side effects.

תרגול: הרץ את `dotnet test` והסבר את ארבעת התרחישים: סינון, קלט לא תקין, שינוי סטטוס עם audit/cache invalidation, ו־Version מיושן. ציין ש־SQLite הוא תחליף יחסי ולא מאמת התנהגות ייחודית של PostgreSQL כמו `ILIKE`.

שאלת ראיון: מה הופך בדיקה למשמעותית, ואיזה סיכון נשאר אם משתמשים בספק מסד אחר בבדיקות?

### מפגש 10 – תכנון, החלטות וראיון מדומה

חזור על פירוק דרישות למשימות, תלויות, הערכת מאמץ, הגדרת תוצרים, trade-offs, מגבלות ותיעוד. הכן הצגה של 5 דקות: בעיה, ארכיטקטורה, שתי החלטות, סיכון אחד, מה נבדק, ומה היית משפר בהמשך. תרגל טבלת Tasks/Stories הכוללת תוצר, סדר, תלות, הערכת מאמץ וקישור לדרישת המקור; כלול בה גם DB, performance, tests, docs ופריסה.

תרגול: הסבר את הבחירה ב־PostgreSQL/EF Core מול חלופות, ב־optimistic concurrency מול נעילות, וב־SQLite לבדיקות מול PostgreSQL ייעודי. אמור במפורש אילו טענות מדדת ואילו הן הצעות לשיפור בלבד.

## בדיקה עצמית לפני הראיון

- האם אפשר לתאר את מסלול הבקשה והאחריות של כל שכבה בלי לפתוח את הקוד?
- האם אפשר להסביר את ה־SQL שה־API מייצר ואת האינדקסים לפי תרחיש שימוש?
- האם אפשר להדגים stale version, audit, validation ותוצאת HTTP לכל מקרה?
- האם אפשר להסביר debounce וביטול בקשות בחיפוש Angular?
- האם אפשר להבדיל בין עובדה שנבדקה, הנחה, מגבלה והצעת שיפור?
- האם אפשר לדבר על חלופות והמחיר של כל החלטה, ולא רק למנות טכנולוגיות?
